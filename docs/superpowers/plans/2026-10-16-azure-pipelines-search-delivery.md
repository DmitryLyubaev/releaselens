# Project 8: Azure Pipelines Search Delivery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Demonstrate one measured, approved search release through Azure Pipelines, a real blocked-quality candidate, one scheduled verification and verified cleanup.

**Architecture:** Package the frozen Project 2 inputs and reusable scoring into one private, digest-bound release. Separate Terraform states control a fresh Basic service and its test/demo-prod schemas; workload-federated agents apply separately saved plans and load the same documents. An independent owner controller enforces the live window and cleanup.

**Tech Stack:** Python/httpx/NumPy/pytest, Terraform 1.15.8, AzureRM 5.7.0, AzAPI 2.8.0, Azure CLI 2.81.0, Azure Pipelines YAML, the immutable Project 7 agent base and GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-15-azure-pipelines-search-delivery-design.md`

Status: implementation plan for review, 16 October 2026. Design approval is recorded in the spec. No implementation, public push, identity mutation, embedding call or live deployment has been performed under this plan.

## Global Constraints

- CV demonstration; one fresh Basic service, test/demo-prod indexes, separate environments and index states. Shared-service logical separation is explicit.
- S2 only: 229 exact audited qids, 41,825 exact corpus chunks, 1,536-dimensional small-model vectors; at least 120 correct top-1 and zero errors/skips/missing results. MRR 0.637 is not an accuracy floor.
- Reuse corpus vectors; at most one separately approved preparation batch for the 229 missing query vectors using `text-embedding-3-small`, model version `1`. No delivery-time embeddings, new questions, chat calls or semantic ranker.
- Exactly four live sets of 229 retrieval calls: positive test, positive prod, negative test and scheduled prod. No request retries, seed replay, corrective apply or automatic promotion retry.
- Source stays on protected GitHub main. Existing P2/P5/P6/P7 evidence, frozen controllers, infrastructure state and deployment workflows retain ownership. Do not re-enable P7 pipeline 1.
- No new Function app, APIM, App Service, Postgres, Artifacts feed or repository migration. Docker-dependent integration tests stay in GitHub CI.
- Separate approvals remain for public code/image publication, account/identity configuration, paid preparation and a costed live attempt; final public evidence publication is also separate.
- Never print private corpus text, account identifiers/URLs, tokens, raw plans/state or cloud errors. Private originals retain failures and true source/time provenance. No em dashes in drafted prose.

## Review Focus

1. Duplicate/missing qids or changed question text paired with valid-looking vectors must refuse before any network call (Task 1).
2. A high aggregate score with one missing, errored or skipped case must fail; a zero-file result publisher must fail too (Tasks 2 and 5).
3. A valid plan for the wrong target, stale state or altered bundle must refuse before any mutation, including uploads (Task 3).
4. Expiry, duplicate dispatch, watchdog death or cleanup timeout must never create stop authority, replay work or expand deletion ownership (Task 6).
5. HTTP success with a partial upload, a delayed count or an untrusted endpoint must not become a false successful release or leak authorization headers (Tasks 1 and 2).
